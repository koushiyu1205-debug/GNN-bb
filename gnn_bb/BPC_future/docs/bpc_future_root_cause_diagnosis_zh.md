## 一句话结论

目前最有证据支撑的根因是：

> 5/10 规模失败的根因是固定开销敏感；20 规模失败的根因不是完全找不到 true-RC negative columns，而是 returned JourneyColumn batch 的 task-set / signature / timing composition 与 RMP active-basis trajectory 强耦合。现有主线还没有一个经过生产 A/B 验证的、低开销、addition-before 的 selector，能够稳定判断哪些负列 batch 会真正改善后续 RMP / dual / pricing trajectory。

因此，“做了很多仍不行”的原因不是某个 Pulse 子模块没调好，也不是简单把 worker 跑久一点、return 多一点、profile-DP cap 调大一点就能解决。

## selector 泛化失败：问题不只是 RC 阈值

更后续的 returned-batch trajectory / selector 审计把问题进一步收紧到
`trajectory selector`：

```text

immediate-addition leave-one-dataset precision = 0.4855769230769231
next-RMP movement leave-one-dataset precision = 0.4794007490636704
hindsight trajectory leave-one-dataset precision = 0.6821705426356589
```

含义是：

- addition 前可见特征有信号，但不够；
- immediate RMP movement 也不够；
- 真正区分 improved / worsened 的是后续 trajectory；
- 但 hindsight trajectory 不能在线使用。

batch / candidate selector 的泛化也失败：

```text
candidate_rows = 2096

single-threshold tp/fn = 3/550
two-feature tp/fp = 427/154
two-feature other held-out datasets tp = 0
candidate selector models strict gate passing models = []
matched-context strict mixed_group_count = 8
exact context conflict_group_count = 12
```

所以当前不能把下面任一规则接成 production selector：

- more negative true RC；
- more returned columns；
- new task set；
- active support-changing；
- low/high active overlap；
- single threshold；
- two-feature same-sample rule；
- simple nearest-centroid / shallow-tree model。

当前最准确的根因表述是：

> 20-task 的有效改进依赖 concrete JourneyColumn batch 是否把后续 1-2 轮
> RMP active basis / dual movement / residual pricing tail 推向 incumbent-producing
> trajectory。现有 addition-before 特征只能解释部分样本，不能跨 instance /
> dataset / profile 稳定泛化。

这也是为什么“做了很多工作都不行”：我们已经能找到负列、加负列、扰动 RMP，
甚至在单 context 中找到 high-impact batch；但还没有一个在线可见且可泛化的规则，
能稳定选择那些会改善后续轨迹的 batch，同时又对 5/10 近似零开销。

## 已经排除的错误解释

| 解释 | 当前证据为什么不支持 |
|---|---|
| Pulse 接线不安全 | materialization、true-RC、certificate guard、duplicate/incomplete 边界已有 focused tests 和日志约束 |
| 只要找到更多负列就会优化 | worker 能加列，但 Phase 7O / 8Q 没有稳定 wall-time ROI |
| 只要扩大 worker budget | 5/10 固定开销会回退，20 capture 对 `pricing_time_limit` 很敏感 |
| 只要 return 更多列 | return8/return12 有时改善、有时恶化，returned count 是扰动器，不是 selector |
| 只要按更负 RC 排序 | exact replay 与 candidate audit 显示更负 RC 可能 worsened 或 replacement |
| 只要上简单 ML selector | simple models / two-feature rules 在同样本或部分 holdout 有信号，但跨 dataset / instance 不稳定 |
| 只要看 immediate RMP movement | next-RMP movement 的 leave-one-dataset precision 仍低，强 objective drop 也可能进入 incomplete-heavy path |

## 当前最可信根因

更精确地说，当前根因是：

> returned JourneyColumn batch 的 task-set / signature / timing composition 与 RMP active-basis trajectory 强耦合；profile-DP / ordinary pricing 能产生负列，但 returned cut 的 ordering、materialization、truncation 决定了哪些 signature 真正进入 pool。现有主线还没有经过生产验证的 addition-before selector，能够稳定判断这个 batch 是否会改善后续 RMP / dual / pricing trajectory。

这同时解释：

- 为什么 Pulse 可以安全找列但不稳定加速；
- 为什么 return8 / return12 有时有效、有时恶化；
- 为什么 best RC、rough RC、rank、returned count 都不能单独解释 outcome；
- 为什么 5/10 必须 gate 掉真实机制；
- 为什么 20 有局部 high-impact batch，却仍没有 production-safe 优化方向。

## 不能标记完成的原因

用户目标要求的不只是“解释合理”，而是要证明一个优化方向：

1. exactness 不变；
2. 5/10 不退化；
3. 20 规模最优求解明显加速；
4. 不依赖后验信号；
5. 不只是单实例、单 repeat、单 profile 的偶然改善。

当前缺口：

```text

has_20_walltime_speedup_evidence = false

```

因此目标仍未完成，不能把任何现有方向宣传成主线优化。

当前下一步不是继续堆 Pulse 搜索机制，也不是立刻把
`true_reduced_cost <= -12.430587` 这类阈值推进 production A/B，而是：

```text

required_selector_holdouts = context / instance / dataset

```

具体顺序：

1. 继续做 no-certificate-effect exact-context capture / replay，扩大 returned-batch
   treatment 数据集，保留完整 JourneyColumn signature、start time、arc option、
   true dual、cuts、RMP pool snapshot；
2. 只使用 addition-before 可见特征校准 selector，并同时通过 context / instance /

3. selector 通过这些离线门槛后，才进入 full BPC A/B；
4. full BPC A/B 必须先证明 5/10 no-regression，再证明 selected 20 hard repeats 的

在这些门槛之前，任何 selector / worker / return policy 都只能是 calibration-only
或 diagnostic-only，不能作为主线优化方向。
