# BPC_future 修改计划：global RC LB、proof tail 与 GAT 可用化

日期：2026-06-23

## 总判断

专家两份回答和当前日志指向同一个结论：现在要达成 5/10 不退化、20/30/50/100 大幅加速，主攻不能再是“把 GAT 分类精度再抬一点”，而是要把 Journey pricing 从“扫完整个 universe 才能给官方证书”改成“中途也能返回可验证的全局剩余 reduced-cost 下界”，再把这个下界转成 branch-and-bound 可以使用的 corrected node bound。

GAT 不能关，但它的角色必须明确：

- 可以做 true-RC 列的 batch admission、排序、delay、pricing mode hint、branch-impact/risk 排序；
- 不能提供 certificate；
- 不能永久丢列；
- 不能直接作为 official lower bound 或剪枝依据。

后续主验收口径统一使用随机时间窗 60-instance benchmark，而不是旧 `moon_trek_60` hard-set。旧 hard-set 只保留为历史难例诊断，不能再混作 5/10/20/30/50/100 的主目标验收。

该口径已固化在 `BPC_future/logical_graph/random_tw_60_benchmark_contract_zh.md`。

20 规模的实验运行时间可以放宽到 600 秒，用于采集 proof tail、late-negative 和 branch 行为；但最终目标不能放宽：random-TW `tasks_020` 的 60 个实例都要在 200 秒内返回 `OPTIMAL`。

20 规模随机时间窗集合尚未达到 200 秒内 OPTIMAL 的目标；其中 `tasks_020/greedy-anchor/apollo15_20km/...seed61308` 是 canonical 60-instance 集合内的阻塞代表。旧 `moon_trek_60` hard-set 诊断只能说明 proof-tail / late-negative / branch-tail 的机制问题，不能替代新 benchmark 的正式结论。

## 2026-06-24 full600 复测与诊断口径修正

canonical random-TW `tasks_020` 全量 60 实例已按 600 秒单实例预算、`--max-workers 4` 跑完：

- `OPTIMAL = 26/60`
- `OPTIMAL 且 wall <= 200s = 20/60`
- `OPTIMAL 但 wall > 200s = 6/60`
- `EXTERNAL_TIME_LIMIT = 30/60`
- 内部 `TIME_LIMIT = 4/60`

结论没有变化：当前版本离“20 规模 60/60 全部 200 秒内 OPTIMAL”还差很远；放宽到 600 秒只能暴露更多 proof tail，不能把当前算法推到目标状态。

这次 full600 暴露出一个诊断口径问题：默认 `moon_trek_20_smoke.yaml` 没有开启 corrected-bound / tail-action audit 行，因此 `audit_journey_tail_action_controller.py` 对 60 个日志只能得到 `row_count=0`。这不表示没有 A/B/C/D 节点，而是正式 benchmark 没把 Tail Action Controller 分类写出来。

已修正：

- 新增 `journey_tail_action_audit_enabled` 诊断开关；
- canonical 20-task 配置默认打开该诊断开关；
- 该开关只写 `journey_corrected_node_bound_audit` / Tail Action Controller 分类日志；
- 明确保持 `journey_corrected_node_bound_fathom_enabled=false`、`journey_tail_action_early_branch_enabled=false`、`journey_tail_action_no_column_early_branch_enabled=false`，不改变求解、剪枝或提前分支行为。
- canonical 20-task 配置同时默认打开 `journey_branch_candidate_log_top_n=100`，只写 `journey_branch_candidates` top-N 特征，不改变 `journey_branch_candidate_priority` 或实际分支选择。这样下一轮 full600 不会再出现 V22 那种 `candidate_log_branch_count=0`、branch-impact 训练行缺候选特征的问题，也能支持 V44/V106 这类 top100 coverage-gap 采样。

同时，full600 的 late-negative 审计已经能提供有效失败画像：150 秒以后共有 `999` 个 tail event，其中 `true_negative_event_count=947`，`weak_false_negative_event_count=52`；`true_negative_inactive_only=570` 明显多于 `true_negative_active_support_changing=59`。这说明当前长尾主负担不是单纯“找不到负列”，而是后段还在付出大量 true-RC 验证/加入成本，其中多数列没有改变当前 active support。下一步主线应优先围绕 support-aware admission/delay、branch-impact 正例和 child proof-cost，而不是急着全量做 Tier 1 micro-expansion。

## 2026-06-23 关键修正

现在必须把两个概念彻底分开：

- 继续加入负 reduced-cost 列，是为了正确闭合当前节点 LP；在最小化 RMP 中，它只会让 `z_RMP` 下降或不变，不会把 `z_RMP` 抬高到 incumbent 之上。
- frontier / completion-bound refinement，只能改善“剩余未探索 pricing 区域的 reduced-cost 下界”，不能改变当前 RMP objective 本身。

因此 seed61000 的 node 1 不是 Tier 1 micro-expansion 能直接 fathom 的节点：

```text
z_RMP = 580.221453667
UB    ≈ 584.354872
```

即使最终完整证明 `global_remaining_rc_lb >= 0`，该节点下界最多也只能回到 `LB=z_RMP≈580.22145`，仍然低于 UB，不能剪枝。要让这类节点进入可剪枝区间，只能依赖：

- 更好的 incumbent，使 `UB <= z_RMP`；
- 有效割或更强 formulation，使完整 LP 下界上升；
- 更有效分支，使 child 的 LP bound 上升并更快闭合。

V7 当前完成的是“判断什么时候值得 refinement”的诊断层：

- frontier ledger；
- `global_remaining_rc_lb`；
- `fathom_rc_target` gate；
- critical-token 数量；
- frontier 水位分布；
- token bound 安全更新；
- refinement 配置和结果接口；
- Tail Action Controller 的 A/B/C/D 分类日志。

尚未完成的是 Tier 1 真正的算法层：

- critical token 的完整 one-step split；
- 必要时 two-step split；
- 父 token 到所有合法 child region 的覆盖证明；
- 父 token 到所有合法 child region 的原子替换覆盖证明；
- 超时、缺失 child、child bound 缺失、coverage 校验失败时 fail-closed。

Tier 1 只能用于 A 类节点：`z_RMP >= UB - eps`、`fathom_rc_target` 存在、`global_remaining_rc_lb` 有效且 coverage 完整、当前 global floor 仍低于 target、critical token count 小、child 总数可控、coverage 完整。对 seed61000 node 1 这类 D 类节点，消耗 micro-expansion 预算没有意义。

下一阶段不能只做 pricing tail，必须并行推进三条线：

1. 完成严格 gated 的 deterministic Tier 1，用于真正可 fathom 的稀疏低水位节点。
2. 改善节点进入可剪枝区间的能力：incumbent improvement、pricing-compatible cuts、更强 formulation、branch strong-bound gain、child proof cost 和 child ordering。
3. 让 GAT 学习 tail action：继续 CG、final probe、提前 branch、branch pair、child 顺序、incumbent search 的调度，而不是把 GAT 当 certificate 或 Tier 1 正确性来源。

- V7 水位式诊断已接入：final-probe 会先根据 `z_RMP`、incumbent、`R_N` 计算 `fathom_rc_target`；若 `z_RMP < UB - eps`，即使所有 token 都证明到 `g>=0` 也无法 fathom，refinement 会跳过。seed61000 node 1 正是这种情况：`z_RMP=580.221453667`，当时 incumbent 约 `584.354872`，所以 target 为空；同时 active frontier 分布为 `min=-412.683770667`、`second=-412.540795667`、`p05=-405.143052667`、`median=-395.956203667`，说明低水位面积很大，不是单个异常 token。

- V8 Tail Action Controller 已接入 corrected-bound audit 并修复 incumbent 绑定。canonical random-TW 20 `seed61000` 的 220s 复验中，node 1 final retry 在 `198.026044s` 写出：`z_RMP=580.221453667`、incumbent `584.354872`、`global_remaining_rc_lb=-412.683770667`、`tail_action=EARLY_BRANCH`、`fathom_possible_if_rc_zero=false`、`frontier_micro_expansion_attempted=0`。这确认 seed61000 node 1 不属于 A 类 refinement 节点。
- Tail Action Controller 已进一步收紧 A 类判定：即使 `z_RMP >= UB - eps`，只要本轮已有 true-RC 负列，就先 `CONTINUE_COLUMN_GENERATION` 完成 LP closure；若没有 `fathom_rc_target`、global RC LB 无效/coverage 不完整、缺少 global LB，或 global floor 已达到 target，则不会打 `FRONTIER_REFINEMENT` 标签。这样后续 A 类机会统计不会混入“没有可执行 refinement 条件”的行。
- V10 child-priority opt-in 解决了 D 类 early-branch 后的队列顺序问题：node 1 生成的 child 3/4 以 `queue_priority_width=-1` 入队，随后 node 3 被优先处理。但 220s 仍 `EXTERNAL_TIME_LIMIT`，node 3 在 `216.582741s` 进入 completion-bound retry，说明阻塞转移到 child proof tail。
- V11b no-column D 类 opt-in 验证了新的边界：root 因 `min_depth=2` 没有被误分支，node 3 在 `196.221668s` 以 `tail_action_no_column=true` 提前分支，跳过了 V10 的 node 3 completion-bound retry；但 300s 仍 `EXTERNAL_TIME_LIMIT`。后续卡在 node 4 的 cg1 local no-column retry 和 node 5 更深层搜索，因此不能把 V11b 当成 20 规模加速已达成。

## 修改主线 A：先让 proof/bound 变成可用的 exact-safe 加速

### A1. 完整化 frontier coverage

目标：让 incomplete/tail 状态也能安全给出 `global_remaining_rc_lb`，而不是只有 exhaustive no-negative 才有证书。

必须覆盖：

- OPEN direct labels；
- lazy next-sortie/profile generation；
- pending complete candidates；
- resume heap / physical catalog；
- worker shard root；
- start-time / path-option 未展开区域。

规则：

- 每个未探索 region 必须有 admissible lower bound token；
- region 展开采用 parent -> children 原子替换；
- pending complete candidate 必须计入 `pending_complete_min_rc`；
- 任何 unsupported region 都 fail closed；
- 不能把统计字段 `lb_min_value` 当成全局证书。

### A2. corrected node bound 从 audit 到 guarded fathom

阶段顺序：

1. V0/V1：只输出 proof artifact，不改变行为。已完成第一版。
2. V2：当 `global_remaining_rc_lb >= -eps` 且 coverage complete 时，允许非 exhaustive no-negative certificate。已有接口和 focused test。
3. V3：当 corrected LB 足以超过 incumbent 时，允许 safe fathom。已完成默认关闭的最小 opt-in，尚未跑 canonical random-TW 20 规模验证。
4. V4：把 `lower_bound_exact` 拆成：
   - `lower_bound_valid`
   - `full_lp_closed`
   - `lower_bound_kind`

安全条件：

- pricing 必须是 global-certificate capable；
- 没有返回 true-negative journey；
- coverage complete；
- unsupported region 为 0；
- `R_N` 来自当前 RMP solve 的 fleet RHS；
- proof artifact 写入 dual/cut/branch hash。

### A3. late-negative tail 单独处理

V2 暴露出的问题是：部分节点不是“没有负列但证不完”，而是后段还持续发现真实负列或 weak/boundary filtered 列。

这里要做两件事：

- 对 true-RC negative：更早批量加入会改变 active support 的列，减少 CG 轮数。
- 对 weak/profile false negative：把重复 rough-negative 形态降权或 delay，减少无效 materialization。

这部分仍然 exact-safe：所有加入列必须 true-RC 验证；所有 delay queue 在 certificate 前必须有 deterministic fallback 释放。

## 修改主线 B：GAT 保留，但改成服务 proof CPU

### B1. v154 继续保留的能力

- true-RC filter；
- candidate ranking；
- kNN/OOD safety shell；
- hard-negative suppression；
- batch admission 的基础 embedding。

旧 5000 样本不重来，作为 base dataset 保留。

### B2. 新增 label namespace

追加 branch-tail / proof-tail intervention rows，不把旧样本硬改成新标签。

新标签包括：

- `y_useful_tail_reduction`
- child negative pricing events
- child CB retries
- child early-branch triggers
- active-support-changing probability
- weak-negative filtered risk
- time-to-next-official-bound / corrected-bound gain

当前关键缺口是 `y_useful_tail_reduction = 0`，所以不能直接训练 production branch GAT。

### B3. 先采正例，再训练

正例采集方式：

- 同一 parent snapshot；
- 固定 RMP pool、cuts、dual、incumbent、branch history；
- 对多个 Ryan-Foster pair 做 forced-pair / depth-scoped forced-pair A/B；
- 每个 child 用固定 expansion 预算，wall time 只做保护；
- 记录 corrected LB gain、negative pricing events、CB retry、expansions、active basis change。

未闭合 child 是 censored 样本，不直接标 0。

## 分阶段落地计划

### Phase 1：补齐 exact-safe proof artifact

- 完成 frontier ledger 对所有未探索区域的覆盖。
- 对 unsupported region 给出明确 reason。
- 增加 5-task exhaustive audit：reported LB 永远不能超过真实 remaining RC。
- 继续保持默认不剪枝。
- 完成 Tier 1 token split 的 fail-closed 算法层：
  - 对父 token 枚举所有合法下一步，包括继续当前 sortie、结束当前 sortie、开始下一 sortie、下一 sortie 的合法首任务，以及当前状态允许的终止分支；
  - 对每个 child 计算安全 bound：`LB_child = max(LB_parent, LB_child_raw)`；
  - 必须先生成全部 children、验证覆盖完整、注册全部 child token，最后才能注销 parent token；
  - 任一 child 超限、超时、无法生成、无安全 bound 或 coverage 校验失败时，父 token 保持不变；
  - 无 `fathom_rc_target` 或 critical token 超限时，refinement 调用次数必须为 0。

验收：

- 5/10 默认关闭行为一致；
- opt-in audit 无越界；
- 日志能区分 exhaustive certificate、frontier certificate、corrected bound、incomplete。
- 小规模穷举验证中，split 后不能漏掉任何可行 journey region；`LB_new >= LB_old`，且始终不超过该 region 的真实最小 reduced cost。
- 任意中断点 ledger coverage 完整；至少在一批 `z_RMP >= UB` 节点上观察到 `global_remaining_rc_lb`、`corrected_node_lb` 和 corrected-bound fathom 明显改善，且 refinement CPU 小于节省的 final-probe/节点搜索 CPU。

### Phase 2：解决 late-negative / weak-negative tail

- 解析 cg 后段 true-negative task-set 是否重复、是否只替换 inactive、是否 active-support changing。
- 对 true-RC verified columns 做 support-aware batch admission。
- 对 repeated weak rough-negative 做 delay/risk 降权。
- certificate 前强制释放 delayed true-negative queue。

验收：

- 10-task tranq 不再在 weak-negative / late-negative tail 处卡死；
- 20-task root CG 轮数、exact pricing calls、weak materialization 时间下降。

### Phase 3：guarded corrected-bound fathom

- corrected LB 在 opt-in 下参与 node lower bound。
- 只有 proof artifact 完整时允许 fathom。
- OPTIMAL 报告必须写清楚 proof source。

验收：

- 5/10 全量 no-regression；
- 20 规模至少出现非 exhaustive corrected-bound 有效剪枝；
- 不允许 heuristic/GAT 作为剪枝证书。

### Phase 4：branch counterfactual probes

- Stage A：每个 parent 6 个候选，两个 child，各 10k-25k expansions。
- Stage B：Top2 加深到 75k-150k expansions，最多 2-3 个 CG round。
- Gold tranche：只对少量 parent 做 5s/child 长 horizon。

验收：

- 产生 `y_useful_tail_reduction > 0` 的正例；
- 能区分“pool width 小但 proof tail 不降”的候选；
- 输出可训练 pairwise/survival/ranking 数据。

### Phase 5：GAT branch-impact / admission opt-in

- 多头训练：旧 admission head + 新 branch/proof head。
- online shadow 先只打分不改变选择。
- opt-in 后只改变排序/加入顺序/触发时机，不改变 exact-safe 证书链。

验收：

- 5/10 不退化；
- 20 paired A/B wall time 下降；
- exact pricing expansions、CB retry、proof-tail p90/p95 下降。

## 分规模目标

### 主 benchmark 口径

后续所有规模主测试均使用随机时间窗 60-instance 集合：

- 每个规模 60 个实例；
- 2 个地形：`apollo15_20km`、`tranquillitatis_balmer_like_20km`；
- 3 种时间窗模式：`greedy-anchor`、`random-wave`、`sector-wave`；
- 每个地形/时间窗模式 10 个实例。

旧 `moon_trek_60` hard-set、`tranq10_01`、旧 `greedy/apollo20` 等只作为诊断补充，用来解释 proof-tail 机制或复现历史问题，不作为最终 no-regression / speedup gate。

### 5 / 10

- 不退化是硬门槛；
- OPTIMAL、objective、certificate source、gap、节点数、RMP solves、pricing calls 不应明显恶化；
- 默认关闭时行为应一致。
- 当前随机时间窗 60-instance 600s 复跑结果：
  - 5 规模：60/60 OPTIMAL，avg `0.347385s`，旧基线 `0.321070s`；
  - 10 规模：60/60 OPTIMAL，avg `5.479933s`，旧基线 `5.030619s`；
  - correctness 未退化，但 10 规模已有约 `+8.9%` runtime tax，后续要作为 guard。

### 20

- 目标：随机时间窗 60-instance 20 规模在 200 秒内 OPTIMAL；
- 实验/诊断预算：per-instance 可以跑 600 秒，用来观察失败尾部和生成训练/审计标签；
- 正式 gate：per-instance 仍按 200 秒验收，且必须 60/60 OPTIMAL；
- 必须有 official dual bound 和可审计 proof artifact；

### A4. Tail Action Controller

先把节点分成四类，再决定是否 refinement：

- A 类：`z_RMP >= UB - eps`、`fathom_rc_target` 存在、global RC LB 有效且 coverage 完整、当前 global floor 低于 target，且 critical token / floor multiplicity 都小。执行 Tier 1 micro-expansion、local unique-route / route-aware refinement，尝试抬高 global floor 并直接 fathom。
- B 类：`z_RMP >= UB - eps` 但几百/几千 token 低于 target。不要逐 token refinement；改做 aggregate route-aware bound、更强 completion relaxation、更紧 cuts/formulation 或 token region 重组。
- C 类：`z_RMP < UB - eps` 且 CG 仍找到有用负列。继续短预算 pricing / GAT admission 以完成 LP closure，但这不会提高 `z_RMP`。
- D 类：`z_RMP < UB - eps` 且 CG 已拖尾。执行 exact-safe early branch；不把当前 RMP objective 当 exact node bound，不用它剪枝，子节点仍靠 exact pricing closure。

补充边界：只要本轮 exact pricing 已经返回 true-RC 负列，即使当前 `z_RMP >= UB - eps`，该轮也还不是 final-probe refinement 机会；必须先把负列加入 RMP 并继续 LP closure，因为加入负列可能让后续 `z_RMP` 下降到 incumbent 以下。

控制器分类已和执行层必要条件对齐：`FRONTIER_REFINEMENT` 不再只由 `z_RMP >= UB` 和 critical token 数决定，还要求 target 存在、frontier LB valid、coverage complete、global floor 未达 target；否则记录为 fallback/continue 原因，不进入 A 类机会统计。


该入口只在显式 opt-in 时使用外部 score map 对 Ryan-Foster 候选排序；`branch_score` 的排序范围仍受 `journey_branch_fractionality_tie_tolerance` 控制，缺少 score 的候选会回退到原 deterministic fractionality 顺序。`branch_score_horizon` 也是显式 opt-in，但会在当前候选中寻找正分 scored candidate，并把排序 horizon 最小放宽到覆盖该 scored candidate，默认最大只到 `journey_branch_candidate_score_horizon_tie_tolerance=0.2`；负分 scored candidate 不会触发 horizon 扩展，也不参与 horizon 优先排序，只按原 deterministic fractionality fallback 处理。score key 支持全局 pair、depth-specific pair、node+depth-specific pair，例如 `1,2`、`depth:0:1,2`、`node:9:depth:0:1,2`。日志中的 `journey_branch_candidates.selected/priority_top` 会记录 `branch_score` 和 `branch_score_source`，并额外记录 `effective_tie_tolerance` / `effective_eligible_count`。
