我提供的参考是：

> **kNN/OOD 可以适度放宽，但不能全局一次性放宽，更不能直接进入 official benchmark。最安全的做法是：先在“pricing 搜索优先级”层放宽，再在“RMP 加列 admission”层小步放宽。**

因为 GAT+kNN/OOD 的核心作用是安全壳。当前代码里，`HIGH_PRIORITY` 需要同时通过 batch 阈值、candidate 阈值、kNN 邻域安全、OOD 半径、安全 fallback 等条件；否则进入 `DELAY_QUEUE`。默认参数里 `knn_k=3`，`max_neighbor_delay_fraction=0.0`，也就是最近邻里只要有 unsafe/delay 信号就非常保守。

---

# 1. 放宽后会发生什么？

放宽 kNN/OOD 后，直接效果是：

```text
HIGH_PRIORITY 数量 ↑
DELAY_QUEUE 数量 ↓
GAT 对 pricing / RMP 的影响变强
```

可能带来的好处：

```text
1. pricing 更快搜到 high-impact residual family；
2. 更多 true-RC negative 列能及时进入 RMP；
3. 减少“好列被过度 delay”的情况；
4. 20-task 可能更快改善 incumbent；
5. 如果 GAT 判断准确，可能减少 tail retry。
```

但风险也很明显：

```text
1. unsafe batch 被错误放行；
2. replacement-heavy / low-ROI 列进入 RMP；
3. RMP 列池膨胀；
4. dual / basis 震荡重新变严重；
5. final judge tail 变长；
6. 20-task primal 可能改善，但 official dual bound 更难出来。
```

所以放宽不是“越松越快”，而是：

```text
太紧：安全但没有 ROI；
太松：看似加速，但可能制造更长拖尾。
```

---

# 2. 精确性会不会被破坏？

一般来说，**只要所有进入 RMP 的列仍然是合法 JourneyColumn，并且最终 proof 仍由 exact pricing full scan 完成，放宽 kNN/OOD 本身不会破坏数学精确性**。

但它可能严重影响求解效率。

也就是说：

```text
放宽 kNN/OOD 的主要风险：
    performance risk / tail risk

不是：
    lower-bound correctness risk
```

前提是必须继续保持：

```text
GAT 不是 pricing oracle；
GAT 不产生 certificate；
GAT 不产生 official lower bound；
GAT 不永久丢弃 true-RC negative；
final certificate 仍由 exact pricing / final judge 完成。
```

你的目标模式计划也明确要求：GAT 只能改变搜索顺序和 admission priority，不能改变 official pricing universe；`DELAY_QUEUE` 是有限延迟，不是 reject；final certificate 只能来自 exact pricing exhaustive no-negative result。

# 3. 现在最危险的不是“能不能放宽”，而是“放宽后有没有 ROI”

你现在最新训练报告里已经显示：当前 batch-impact checkpoint 还没有通过 Stage 4，blocker 包括：

```text
accepted_batch_roi_below_baseline_margin
knn_ood_audit_missing
major_family_coverage_incomplete
stage3_effective_sample_count_below_200
safe_precision_below_threshold_or_no_accepted_batches
```

并且当前数据主要是 `sector-wave`，还缺 `random-wave / greedy-anchor` 覆盖。

所以现在不能简单说：

```text
把 kNN/OOD 放宽一点就能大幅加速。
```

更准确是：

> **可以做受控放宽实验，但必须用 precision + accepted ROI + tail 指标一起判断。**

# 4. 哪些参数可以放宽？

当前 kNN/OOD 安全壳主要有这些控制项。

## 4.1 `max_neighbor_delay_fraction`

当前默认：

```text
max_neighbor_delay_fraction = 0.0
```

含义是：

```text
最近邻里只要出现 delay/unsafe 信号，就不放行。
```

放宽方式：

```text
0.0 → 1/k
```

例如：

```text
k = 3 时，允许 1 个 unsafe neighbor：
max_neighbor_delay_fraction ≈ 0.34
```

但我不建议一开始就这么大。更稳的是：

```text
k = 5, max_neighbor_delay_fraction = 0.2
```

含义：

```text
最多允许 5 个邻居里 1 个 unsafe。
```

风险：

```text
会显著提高 HIGH_PRIORITY 数量，但 false-safe 风险也会变高。
```

---

## 4.2 `safe_radius_multiplier`

当前 OOD 检查是：

```text
nearest_safe_distance <= safe_radius
```

如果放宽：

```text
safe_radius_multiplier: 1.0 → 1.1 / 1.2 / 1.5
```

就会允许更远的样本被认为 in-distribution。

作用：

```text
减少 OOD delay；
增加 high-priority coverage。
```

风险：

```text
把训练分布外的 branch/tail/family 状态误认为安全。
```

---

## 4.3 `batch_threshold`

这是 batch-level gate：

```text
batch_score >= batch_threshold
```

如果降低它：

```text
更多 batch 可以通过第一关。
```

风险：

```text
低 ROI batch 被放行。
```

如果你要放宽，我建议先只小幅降低：

```text
降低 0.02 ~ 0.05
```

不要一下从高阈值降到 0.5。

---

## 4.4 `candidate_threshold`

这是 candidate-level gate：

```text
candidate high_priority score >= candidate_threshold
```

降低它会让更多 candidate 被选为 high priority。

风险：

```text
candidate-level false high priority 上升。
```

当前 decision 逻辑里，如果 candidate false high-priority on delay 发生，会直接转 delay。代码的 `_classify_record()` 里要求 `candidate_fp == 0` 才能最终 HIGH_PRIORITY。

---

## 4.5 `candidate_delay_risk_threshold`

如果启用 delay-risk gate：

```text
delay_risk_probability > threshold
    → block HIGH_PRIORITY
```

放宽它会让更多存在 delay-risk 的 candidate 通过。

这个参数要很小心。
我建议：

```text
不要优先放宽 delay-risk gate。
```

因为这个 head 本来就是为了避免 bad mode / tail risk。

---

# 5. 我建议怎么放宽？

不要全局放宽。按两个通道分开。

---

## 通道 A：搜索优先级可以先放宽

这是最安全的。

意思是：

```text
GAT+kNN/OOD 判出来的 high-priority family
只用来引导 pricing 先搜哪里，
不直接决定加入 RMP。
```

即使 GAT 判断错了，最多只是：

```text
pricing 先搜了一个不太好的区域
```

但 exact pricing 仍然会 true-RC 验证，最终 full fallback 也还在。

所以这里可以更大胆一些：

```text
kNN/OOD 放宽版 → pricing priority
严格版 → RMP admission
```

---

## 通道 B：RMP admission 要更严格

真正把列加入 RMP 时要保守。

建议：

```text
HIGH_PRIORITY 加入 RMP:
    用严格 kNN/OOD

搜索优先级:
    可以用较宽松 kNN/OOD
```

也就是：

```text
同一个 GAT 输出，分两套阈值：
    discovery_thresholds   比较松
    admission_thresholds   比较严
```

这样可以兼顾：

```text
找列快
+
加列稳
```

# 6. 推荐的三档实验配置

## Profile 1：Strict / 安全基线

用于 admission。

```text
knn_k = 3 或 5
max_neighbor_delay_fraction = 0.0
safe_radius_multiplier = 1.0
batch_threshold = training selected threshold
candidate_threshold = training selected threshold
candidate_delay_gate_enabled = True
```

目标：

```text
false high-priority ≈ 0
safe precision 高
accepted batch 少但可靠
```

---

## Profile 2：Balanced / 搜索优先级

用于 pricing priority，不直接用于 RMP admission。

```text
knn_k = 5
max_neighbor_delay_fraction = 0.2
safe_radius_multiplier = 1.1 或 1.2
batch_threshold = selected_threshold - 0.02
candidate_threshold = selected_threshold - 0.02
candidate_delay_gate_enabled = True
```

目标：

```text
提高 candidate coverage；
观察是否减少 generated_sequences / evaluated_timed_trips。
```

---

## Profile 3：Exploration / shadow only

只能 shadow，不能加列。

```text
knn_k = 5 或 7
max_neighbor_delay_fraction = 0.25 ~ 0.33
safe_radius_multiplier = 1.5
batch_threshold = selected_threshold - 0.05
candidate_threshold = selected_threshold - 0.05
```

目标：

```text
看放宽后能发现多少潜在 high-ROI family。
```

不能直接进入 official RMP admission。

# 7. 放宽是否可行，要看哪些指标？

不能只看：

```text
HIGH_PRIORITY 数量增加
```

必须看三类指标。

## 7.1 Precision / Safety

```text
high_priority_precision
safe_precision
false_high_priority_on_delay
false_safe_rate_union
accepted bad mode count
OOD accepted count
kNN unsafe accepted count
```

如果这些变坏，不能上线。

---

## 7.2 Productivity / Coverage

```text
accepted_batch_count
accepted_batch_rate
predicted_high_priority_count
family-level accepted count
delay rate
coverage_non_ood
```

如果 accepted count 仍然接近 0，说明还是太保守。

---

## 7.3 Solver ROI

```text
20-task wall-time
time to incumbent
time to official dual bound
generated_sequences
evaluated_timed_trips
pricing_calls
exact_pricing_calls
RMP solves
certificate_no_column_rounds
final_judge_retry_count
hidden_negative_count
accepted_batch_roi
```

如果 primal 变好但：

```text
dual_bound 还是 None
final_judge_retry_count 增加
exact_pricing_calls 增加
RMP pool 变大
```

那就是假加速。

你的计划里也明确要求训练/测试必须同时看 high-priority precision、accepted batch ROI、false-safe、accepted coverage、5/10 no-regression 和 20-task ROI，而不是只看 F1 或 recall。

# 8. 放宽后 delay queue 怎么处理？

如果放宽导致更多列变成 HIGH_PRIORITY，delay queue 会变小。
但所有被判为 DELAY_QUEUE 的 true-RC negative 仍然不能丢。

规则不变：

```text
DELAY_QUEUE 不是 reject；
certificate 前必须用 current true dual 重新计算 rc；
当前仍为负 → 加入 RMP 或 re-expose；
当前不为负 → 不阻塞当前 certificate，可移出 active queue / archive。
```

放宽 kNN/OOD 不改变这个规则。

---

# 9. 什么情况下可以正式放宽？

我建议满足以下条件后才让放宽版进入 opt-in online：

```text
1. 5/10 no-regression 通过；
2. validation safe_precision >= 0.90；
3. false_high_priority_on_delay <= 1%；
4. accepted_batch_count > 0；
5. accepted_batch_roi > baseline + margin；
6. family holdout 不崩；
7. 20-task shadow 显示 tail retry 或 pricing workload 下降；
8. certificate safety test 通过。
```

否则只能做：

```text
offline audit
shadow
pricing-priority-only
```

不能 admission。

---

# 10. 我的建议

你可以放宽，但按这个顺序：

```text
第一步：
    在 shadow 中放宽 kNN/OOD，观察 HIGH_PRIORITY 增量和 false-safe。

第二步：
    只把放宽版用于 pricing priority，不直接加 RMP。

第三步：
    如果 20-task pricing workload / tail 指标改善，再把小幅放宽版用于 admission top-K。

第四步：
    certificate mode 仍然完全关闭 GAT hard filtering。
```

最稳妥的策略是：

```text
宽松 shell 用于“先搜哪里”；
严格 shell 用于“是否加进 RMP”。
```

---

# 11. 最短回答

> **可行，但必须受控放宽。放宽 kNN/OOD 会增加 HIGH_PRIORITY 数量，提高搜索覆盖和潜在 ROI；但也会增加 false-safe，把低质量或拖尾风险列放进 RMP，可能导致 dual 震荡和 final proof 更慢。最安全的做法是先把放宽版只用于 pricing 搜索优先级，而不是直接 admission；真正加列仍用更严格的 kNN/OOD。只有当 high-priority precision、accepted batch ROI、false-safe rate、5/10 no-regression 和 20-task tail ROI 都通过后，才能把放宽版本进入 opt-in online。最终 certificate mode 仍必须关闭 GAT hard filtering，由 exact pricing full scan 证明。**
